# Contributing

Thanks for looking. The most useful contributions are new checks and new providers.

## Setup

```
python -m venv .venv && .venv\Scripts\activate
pip install -e ".[dev,azure]"
pytest
fedramp-viz serve --source samples/azure-sample.json
```

## Adding a check

1. Pick the module in `fedramp_viz/rules/azure/` that matches the service, or add one and import it in `rules/azure/__init__.py`.
2. Decorate a function with `@rule(...)`. Use the control ids as NIST spells them (`SC-7(5)`, not `SC-7.5`). Set `min_level` to the lowest impact level where the setting is actually expected; leave it at Low for baseline hygiene like TLS and HTTPS.
3. Return `passed`, `failed`, `manual` or `not_applicable`. Use `manual` when the inventory cannot decide, never as a soft fail.
4. Write the remediation as the command or portal step someone would actually run.
5. Add a case to `samples/azure-sample.json` that exercises both outcomes and a test in `tests/test_rules.py`.

Keep the mapping honest. A check gives evidence for a control; it does not satisfy the control. If a mapping is a stretch, leave it out.

## Adding a provider

See "Adding a provider" in the README. Keep provider SDKs as optional extras in `pyproject.toml` so the base install stays small.

## Style

* Python 3.11 or newer, type hints, no framework beyond FastAPI.
* The dashboard is plain HTML, CSS and JavaScript with no build step and no external resources; it must keep working under the Content Security Policy in `api.py`.
* Insert anything that came from an API into the DOM with `textContent`.
* Plain language in messages and docs. No em dashes.
* One logical change per commit, tests passing.

## Regenerating the catalog

`fedramp_viz/data/controls.json` is generated by `scripts/build_catalog.py` from the OSCAL profiles in `baselines/`. Do not hand edit it. If FedRAMP publishes a new baseline revision, replace the profiles and rerun the script.
